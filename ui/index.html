    What framed does

    framed fixes one ticket at a time in an existing repo. You describe the bug in Claude Code; framed finds where it is, checks whether the code there is deliberate, and stops once to ask you. After your yes it writes a test that shows the bug, fixes it, runs the tests, and hands you a pull request to review.

    Every step is committed on the task's own branch, so you can stop at any point and pick up later. The pull request is where a person looks again: anything that needs a decision is listed first in it, under "For the reviewer".

    Getting started

    1. Set up the repo, once

    In Claude Code, say set up framed. It reads the repo and writes a map of its modules and a small config (ticket prefixes, how tests run). They land on the branch framed-init as a pull request. Merge it, and the repo is ready.

    2. Fix a bug

    Paste the ticket or describe the bug, with its key, e.g. APP-1234: the export button does nothing for archived orders. No command is needed. If there's no key, framed asks once. This page opens on Build and follows along.

    3. Starting a new app instead

    In a folder with no code yet, pick a look in Studio, press "Use this design", then say build my design.

    The gate

    framed asks you one question per fix, before any code changes. It comes after Find and Why, so everything that needs a person has been found by then. The question has three parts:

    • Where the bug is and which files change.
    • What changes for the user, and what stays as it is.
    • What it's unsure of: comments that say the code is deliberate, tests that can't run on this machine, anything that goes against the ticket.

    How to answer

    • Yes: it fixes, tests and opens the pull request, and asks nothing more.
    • Anything else ("keep the old message", "don't touch the shared service"): it changes the plan and asks again. A no is never the end; say what's wrong.

    While it waits, the Gate stop on the road is amber and the Build item in the sidebar blinks.

    Build: the road Open Build →

    Each fix is a road with seven stops: Find (where the bug is), Why (is it deliberate?), Gate (your yes), Test (prove the bug), Fix (change the code), Suite (run every test), PR (ready for review).

    ColourMeans
    GreenDone and committed.
    BlueWorking on it now.
    AmberWaiting for you.
    RedFailed or stopped. The note under the road says why.
    GreyNot reached yet.

    Below the road, The trip so far lists each step's note, and the side panels show the plan, decisions, what changed and the blast radius (everything the change could reach). The tokens card counts what the fix has used so far.

    Map Open Map →

    Each bubble is a module of the repo, coloured by language. A solid line means one module imports the other; a dashed line means their files often change together in git history.

    During a fix, the modules it changes glow blue and the ones it may affect ripple amber. Everything else dims. Hover a module to see what it does; click it to open its files.

    Home, Files, Studio

    Home Open →

    One card each for the current fix, the map, the files, your Claude usage and this repo.

    Files Open →

    The modules and their files. Open a file to see what it uses, what uses it, the files that change with it and its tests.

    Studio Open →

    Pick a look, tweak it on the live preview (colours light and dark, fonts, text size, corners, spacing, shadows, motion) and press "Use this design". The readability check flags text that's hard to read. Not liking any? Write what you want and press Refresh looks: the design scout makes six more, which uses tokens.

    Saving builds nothing. Say build my design in Claude Code. In an existing app it changes only the theme (colours, fonts, corners), after one question that lists every file it will change.

    Things you can say

    Plain words in Claude Code; no commands to learn.

    SayWhat happens
    A bug, with its ticket keyA fix starts, or picks up where it stopped if that ticket is already under way.
    set up framedWrites the map and config, as a pull request.
    build my designBuilds the design saved in Studio.
    find more designs for a bakeryThe design scout makes six new looks for Studio.
    open the framed pageOpens this page now.
    turn the framed page off / onOff: it no longer opens by itself. Your choice, kept on your machine, not in the repo.
    install the framed status lineOne line under the chat: the fix's step, context left, and your 5-hour and weekly limits.

    What framed never does

    • Commit or push to the default branch, or force push. A hook checks every git command before it runs, so this holds even if the model forgets.
    • Change your machine to get past a problem: no global installs, PATH changes or new runtimes. If a test can't run here, the pull request says so and opens as a draft.
    • Push to a remote that isn't real. With no remote, it gives you the pull request's title and description to open yourself.
    • Change things outside the ticket. What it notices on the way is written down as "Left as is", with the file and line.
    • Make up test results. The before and after in the pull request are copied from the test runner's own output.

    Where things live

    FileWhat it is
    .framed/config.jsonTicket prefixes, branch names, how the tests run.
    .framed/map.mdThe map: modules, what depends on what, what's surprising.
    .framed/tasks/<TICKET>.mdThe fix's working file: plan, steps, decisions. Committed at every step; becomes the pull request's description, then is deleted.
    .framed/design/Studio's looks and your saved pick. Not committed: it's your picking, not the repo's.
    .framed/design.mdA new app's design rules, which every later build follows.
    ~/.framed/Your own settings: page on or off, which page runs where.
