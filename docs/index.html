A Claude Code plugin · v0.1 · November 2026

framed

An AI dev workflow for the code you already have. It maps a repo, fixes one ticket at a time without breaking what depends on the change, and hands you a pull request with real test output in it. For a new app, it starts from a design you pick.

The code is the spec, the map is how the agent reads it, and every step ends on its own.
map→tier→budgeted steps→working file→PR
brownfield + greenfield one workflow, two ways in 21 public repos the map was stress-tested on 1 question per fix 0 dependencies in the script
Start

Why it exists

Workflow frameworks for AI coding mostly start from an empty folder. Day-to-day work is the opposite: a ticket, a codebase nobody fully remembers, and a fix that must not break the screen next door. These are the problems framed was built around, taken from using other frameworks at work.

Built for greenfieldBrownfield is an afterthought, yet most work is fixing and extending existing code.
Missing testsLegacy code often has none. Frameworks ignore that or try to rebuild coverage up front.
One size of processA one-line fix gets the same heavy process as a new feature.
Files nobody readsPeople click "yes" on generated documents without reading them, and the documents pile up.
Steps that never endA brainstorm runs until you stop it, which hurts when you only get a few sessions.
One fix, three new bugsCode that depends on the change isn't checked, so the fix breaks it.

How it works

The pieces

You talk to Claude Code in plain words; there are no commands to learn. The plugin adds skills that hold the steps, two agents for jobs that need their own budget, hooks for what must never depend on the model remembering, and one Node script for everything mechanical. All state that matters lives in the repo, so a fix survives a closed session.

How a session knows what to do

At every session start a hook reads the repo in about a second and tells the model where things stand. No slash commands: the person says what they want, and the state decides which skill runs.

Repo stateThe person seesThe model then
No code yetPick a look in Studio, save it, say "build my design"Runs design, never map or patch
Code, no setupSay "set up framed" for a one-time scanRuns map
Setup not mergedMerge framed-init, or work from itNever re-runs map
Ready"Tell me the bug", with the ticket prefixesRuns patch on any bug or ticket
Fix in progressThe ticket and step, "say continue"Resumes patch
Next The map →
How it works

The map: how the agent reads a repo

The agent reads the map instead of the whole repo. It is built from three sources a script computes in seconds with no model, plus one budgeted model pass that names the modules in plain words and marks what it is unsure of. The file-level graph stays on the machine; the one-page module map is committed.

Every edge records where it came from, so a reader can tell a resolved import from a guess. During a fix the same graph gives the blast radius: each dependent of a changed file gets a verdict before the fix can end.

Next A fix →
How it works

A fix: seven stops, one question

Everything that needs a person is found before the gate: where the bug is, what depends on it, comments that say the code is deliberate, whether the tests can run here. The gate asks once. After a yes nobody is asked again; anything that needs a decision goes first in the PR under "For the reviewer", and the PR opens as a draft.

Each stop ends on its own, updates the working file and commits, whether it finished, failed or is waiting. That file is the checkpoint, so a closed session picks up where it stopped.

Rules the steps follow

  • The ticket is the scope. What the agent notices beyond it is written as "Left as is", with the file and line, and each note is checked against the code again before the gate.
  • The bug test is the evidence. The PR shows it failing before the fix and passing after, copied from the runner's output. When it can't run here, the PR says so.
  • Coverage follows the work. A project with no tests gets its first one where the fix lands, using the tool the repo already uses for that stack.
  • Never change the machine to get past a problem. No global installs or runtime switches; what can't run is named for the reviewer.
Next The guard →
How it works

The guard: rules in code, not in the prompt

Prompts get ignored under pressure. The git rules are a hook that reads every shell command before it runs, on Bash and PowerShell alike, and refuses the ones that break them. The model gets the reason back and adjusts.

Next Studio →
How it works

Studio: build your own style

Studio is a page for choosing how an app looks: ten built-in styles, or six more from the design scout for a brief you write. Everything is tweakable on a live preview: colours in light and dark, fonts, text size, corners, spacing and motion, with a readability check as you go. Saving builds nothing. "Build my design" in the chat does, and the folder decides which path it takes.

Next The page →
How it works

The page

A local web page served by the script on 127.0.0.1. It opens by itself when a fix, a setup or a Studio build starts, once per ticket, and reuses the repo's running page when there is one. It reads everything and writes nothing except Studio's saved choice, and it accepts requests only from itself on this machine.

PageWhat it shows
HomeThe current fix, the map and the repo at a glance.
BuildThe fix as a road, each stop's note, the plan, decisions, blast radius, and the tokens each stop used.
MapModules as bubbles. Imports are solid lines, changed-together is dashed. The modules a fix changes glow; the ones it may affect ripple.
FilesA module's files: the ones this fix changes, the ones it may affect and why, and each file's direct neighbours and tests.
StudioPick and tweak a design on a live preview.
HelpWhat framed does, the gate, how to read each page, what to say, what it never does. Searchable, every section linkable.
  • An optional status line under the chat shows the step, context left and plan limits.
  • A page with no tab open for 30 minutes stops itself, so old pages don't hold ports, and a second copy never starts on another port.

What we learned

Case study: replaying a real bug

The fairest test of a fixing tool is a bug that was already fixed. The team's fix is the known answer, so the agent's work can be checked against what people actually did.

The codebase and the bug

A real company codebase: a .NET backend serving two React front ends through one shared API, with no unit tests, only browser tests against a deployed site. The bug: a "print" action stayed available for records that were already closed. The ticket asked for three things: disable the button with a reason on hover, have the server refuse the request, and show that reason in the app.

What framed did, stop by stop

  1. Findblast radius
    Found the bug in two places, the server endpoint and one front end's button. The map showed the second front end calls the same endpoint, so the server's refusal was limited to the first app's records and the other app kept working as before.
  2. Whydeliberate code
    Found two comments that argued against the change: the shared service holds nothing app-specific, and a greyed-out button "invites a click that can only be answered with a refusal". It didn't override them quietly. It brought both to the gate as unsure.
  3. Notes checkleft as is
    Re-read the code behind each "Left as is" note before the gate. Nothing needed correcting.
  4. Gateone question
    One question with three parts. One yes, and nothing was asked after it.
  5. Testfirst unit tests
    Set up the repo's first unit test projects, matched to the versions the project already used. The bug test failed first, as it should.
  6. Fix and Suite
    All front-end tests passed and the type-check was clean.
  7. PRdraft
    Before and after test output exactly as the runner printed it, checked line by line against the session's own command output. The backend tests were written but couldn't run on that machine, which lacked the right .NET version. framed didn't install it: it named the gap for the reviewer and opened the PR as a draft.

Use it

Limits

  • The map answers "what might be affected"; tests answer "was it". A map without tests is a confident guess.
  • Static imports can't see calls across repos, logic in the database, behaviour driven by config, or a front end calling an API by URL. Co-change catches some of it; the rest is written in by hand.
  • The guard parses command lines. It covers the normal forms and common disguises, not every shell construction, and it doesn't govern a person at a terminal.
  • Studio builds have been run up to their gate; the build after the yes has not yet been run end to end.
  • One tier, patch, is built. Bigger work and planning steps come later.
  • Version 0.1: proven on replays and stress tests, not yet in day-to-day team use.

Install

framed is open source on GitHub at IsharaaRanasinghe/framed, MIT licensed. You need Claude Code, Git and Node 18 or newer. In Claude Code:

/plugin marketplace add IsharaaRanasinghe/framed /plugin install framed@framed

Or from a terminal:

claude plugin marketplace add IsharaaRanasinghe/framed claude plugin install framed@framed

To update later: claude plugin marketplace update framed, then claude plugin update framed@framed. Restart Claude Code to load the new version.

Then open Claude Code in any repo and say what you want:

SayWhat happens
set up framedMaps an existing repo once, on a framed-init branch to merge.
a ticket or bugStarts a fix: one gate question, then a PR.
continueResumes a fix from its last step.
open the pageShows the road, the map, Studio and Help.
build my designApplies the Studio design to an existing app, or starts a new one.
